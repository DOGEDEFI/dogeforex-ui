# IMF V2 frontend instructions

This isolated frontend belongs to `dogeforex-ui`. The earlier prototypes in `../prototypes/` are separate; do not overwrite them. The source was imported from `../../../dogeforex-institutional/` after its `npm run verify` passed on 2026-10-24. `handoff/source-snapshot.json` records imported hashes.

## Public scope

- Name: **International Multicurrency Framework (IMF)**. Older Factory/Foundry naming is historical.
- Primary journey: project tokens as collateral → mint a currency and record its debt → use a separate project-token allocation for DEX liquidity.
- Three surfaces: website at `https://imf.li/`, documentation at `https://docs.imf.li/` and application at `https://app.imf.li/`. Local review uses ports 5180, 5181 and 5182. `www.imf.li` and `doge.forex` are website redirects, not separate application origins.
- Preserve Chairpup, Scenario/world assets, visual learning, deeper guides, and equivalent human/agent planning. Keep meaningful captions and accessible controls with the imagery.
- Each currency is an independent system. No shared reserve, automatic FX conversion or cross-currency exposure engine is implemented. Collateral assessment and vetoes remain participant responsibilities.
- The protocol is described publicly only as an independent extension of Frankencoin mechanics. Do not restore intermediate-fork naming, claim official affiliation, inherited V2 audit coverage, production availability or MiCA compliance.

Never substitute V1 addresses, teaching amounts or generated fixtures for verified state. Keep unavailable and failed reads distinct from zero. The test-only genesis example describes this USD deployment, not all 11 planning currencies.
- Only the verified `runtime-config` USD DogeOS Chikyū testnet path may prepare guided MetaMask writes. Imported registries and custom RPC connections remain read-only. `config/runtime.json` remains unconfigured/read-only, and the synthetic fixture accepts only its isolated test wallet. - Guided actions cover the 37 canonical operations in `src/actions.ts`: position creation/cloning/minting, management, rolling/ownership/rescue, challenges/auctions, bridge/savings/equity and governance. Use exact approvals, a fresh static call and gas estimate, explicit review and separate MetaMask confirmation for every transaction. Keep the receipt journal, and never resubmit or trigger a follow-up automatically. Simulation reflects current state, not a future guarantee.
- Do not add guardian/allocation-bootstrap dependencies, private-key handling, message signing, DEX execution, keeper automation or agent execution. A read-derived eligibility result or quote alone is not transaction simulation or authorization. tUSDC is a deployer-minted test asset, not production USDC; production readiness is not claimed.
- Amount, price and rate calculations use exact integer strings/BigInt and method-specific units. Browser `Number` is permitted for display percentages only, never raw monetary values.
- Preserve the offline learning model and `imf.position-plan.v1` compatibility separately from operational V2 read models. Ordinary planning exports, including `imf.v2-read-plan.v1`, remain non-executable and never grant authority. Browser storage is local to the app origin.
- `assets/articles.json` contains trusted repository-owned HTML only. Resolve its controlled origin/asset tokens before rendering; do not inject remote or user-provided HTML.

## Static discovery and responsive behavior

- Every guide is generated as complete HTML at `/guides/<id>/` with a unique title, description, canonical URL and `TechArticle`/breadcrumb JSON-LD. The documentation index is static too. Legacy `/#<id>` shortcuts redirect in JavaScript; do not return to hash-only guide content.
- `scripts/discoverability.mjs` owns trusted guide/status rendering, metadata, responsive image markup, robots.txt, sitemap.xml and the experimental llms.txt index. Release-specific guide status must match the selected runtime: configured public reads and guided MetaMask writes cover USD only, imported/custom connections are read-only, tUSDC is not production USDC, DEX support is not implied, and production readiness is unclaimed. Do not imply that schema or llms.txt guarantees indexing, ranking, citations or model training behavior.
- All 11 codes remain planning identifiers. Ecosystem/read-backed options are enabled only for currencies verified against the active registry; unavailable options are labelled and disabled for that workflow. Only verified runtime-config USD may use the guided write path. Keep this distinct from local planning.
- Documentation search failure must not remove static guide content or navigation. Mobile sidebar controls are progressive enhancements: without JavaScript, guide content and navigation stay visible and the main mobile menu remains available. No-JavaScript app views remain non-executing.
- Test 320–1440px layouts across the website, every guide and every workspace view, including the dashboard, arena and teaching review. Include keyboard disclosure controls, no-JavaScript reading and mobile touch contexts. Keep one workspace navigation rail grouped by user intent; dashboard subviews use a single horizontal tablist, never a nested sidebar or mobile menu grid. Preserve tab/tabpanel semantics, Arrow Left/Right and Home/End navigation, active-tab reveal on viewport resize, and the existing `#dashboard/<panel>` deep links. The dashboard follows the standalone prototype's page copy, compact KPI cards, analytical grids, filter chips, dependency-free SVG visuals, methodology dialog and working copy/export controls. Composition uses discovered position counts, not inferred collateral values; CR visuals use stored liquidation parameters, not market prices; history, market feeds and unsupported scores remain designed unavailable states. Responsive PNG derivatives retain the original artwork; their generation does not clear redistribution permissions.
- Generated script URLs are root-relative. App order is site-config, currencies, shared, protocol, planning, offline, wallet, discovery, v2, dashboard, actions, app. `scripts/check-discoverability.py` asserts that order, static guide content, canonical metadata, visible-FAQ/JSON-LD parity and public discovery files. `scripts/prepare-vercel.mjs` rejects stale production status, fixture/mock-provider output and source maps, and packages explicit guide/index redirects plus text/XML content types. The dashboard is read-only and uses the same verified V2 client; historical charts and reference-market feeds remain explicit unavailable states until a real indexer/feed is configured.

## Commands

- Use Node 22 for checks. `npm install` after the sibling SDK has been built.
- `npm run verify`: syntax, separate review/fixture builds, static content/discovery checks, exact-planning and browser-bundle/read-model checks.
- `node scripts/check-actions.mjs`: check all 37 canonical action encodings/decodings and receipt event handling without adding a provider or signer.
- `node scripts/wallet-check.mjs`: exercise isolated wallet policy, preparation, confirmation and receipt-journal boundaries with the test wallet only.
- `node scripts/journey-check.mjs`: exercise the visible guided forms in isolated Chrome against the synthetic fixture and test-only EIP-1193 wallet. Never point it at a real wallet or public DogeOS RPC; use the protocol Hardhat test for actual local-EVM execution.
- From `../../dogeforex-protocol`, `npx hardhat test test/FrontendJourneysV2Tests.ts`: local-only real-contract execution coverage for the frontend journeys. This is not a public testnet transaction or a production certification.
- `npm run build:review`: create separate local website/docs/app roots under `dist/`.
- `npm run dev`: build and serve `http://127.0.0.1:5180/`, `http://127.0.0.1:5181/` and `http://127.0.0.1:5182/`.
- `npm run dev:fixture`: serve the explicitly synthetic fixture on `http://127.0.0.1:5190/`, `http://127.0.0.1:5191/` and `http://127.0.0.1:5192/`. Only its isolated test wallet may exercise synthetic writes; never treat it as deployed or production state.
- `npm run verify:browser`: build both preview types, run isolated-Chrome interactions, screenshots, actual downloads and responsive checks via `playwright-core`. Reuse healthy existing previews without stopping them. If a preferred port range is occupied but unresponsive, select a free three-port range and rebuild the local preview origins to match, so redirects and canonical metadata remain testable. Review and fixture port ranges must remain distinct even when the review preview falls forward to the usual fixture range. `node scripts/browser-check.mjs` runs only the fixture flow; add `--default` for the ordinary unconfigured flow. Set `CHROME_PATH` if Chrome is elsewhere. No existing browser profile is used.
- `npm run verify:testnet`: build the explicit DogeOS testnet MetaMask configuration for the three `imf.li` origins under `.production-dist/`, check its content, package Vercel Build Output bundles under `.vercel-output/`, and run real-Chrome live RPC/read and responsive checks. The checker requires no injected MetaMask, monitors JSON-RPC bodies on all origins and must retain `transactionSent: false`. Do not publish a review or fixture build and do not send public transactions.
- `vercel deploy --prebuilt --prod --archive=tgz --yes --cwd .vercel-output/<surface>`: deploy a linked website/docs/app project. Repackaging preserves Vercel links and local OIDC files; those credentials are excluded from uploads.
- `npm run dns:vercel:dry-run`: compare `config/vercel-dns.json` with Infomaniak without changing records. `npm run dns:vercel:apply` applies the reviewed change set. Keep the Infomaniak token only in ignored `.env` as `INFOMANIAK_API_TOKEN`; never print it or grant unrelated scopes.
- `config/runtime.json` remains deliberately unconfigured for ordinary review. `config/runtime.testnet.json` is the explicit public testnet MetaMask configuration. Neither may contain credentials. The ignored `.env` is only for local deployment credentials and is never part of a site bundle.

Preserve page-specific script loading and the existing IDs/anchors unless updating all associated tests and links. Update this file and the README when behavior or verification status changes. Browser DOM harnesses are not substitutes for actual desktop/mobile, keyboard and accessibility checks.
